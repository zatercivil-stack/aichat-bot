# Кейс: автоматизация обслуживания AI-сервиса

## Задача

Организовать самообслуживание в Telegram: пользователь получает AI-изображение и оплачивает услугу, оператор управляет продуктом через административную панель. Требуется связать внешние AI- и платёжные API с внутренними правилами учёта, подписками и повторными коммуникациями.

## Реализованный процесс

1. Пользователь отправляет фото и выбирает сценарий обработки.
2. Приложение проверяет баланс и списывает кредиты с блокировкой строки пользователя.
3. Сервис обращается к AI-провайдеру. Для части ошибок предусмотрены резервные модели и провайдеры; если результат не получен, обработчик выполняет компенсацию кредитов.
4. При покупке webhook и резервный опрос используют общий обработчик активации. Для YooKassa статус, сумма и идентификатор локального платежа проверяются через API провайдера.
5. Начисление кредитов, активация подписки и изменение статуса платежа выполняются в одной транзакции. Блокировки платежа и пользователя защищают от повторной обработки и потери параллельных начислений.
6. Планировщик запускает коммуникации по условиям: незавершённая оплата, завершённый пробный период, приближение срока кредитов, продление подписки.
7. Оператор видит пользователей, события, платежи и воронку в панели; может менять цены, тексты и пресеты без правки исходников.

## Какие компетенции демонстрирует репозиторий

| Область | Проверяемый результат |
| --- | --- |
| Декомпозиция процесса | Пользовательские состояния, условия фоновых задач, отделение обработчиков от сервисов и репозиториев |
| Внедрение ИИ | Интеграции нескольких API, обработка ошибок, резервные модели, учёт стоимости операций |
| Платёжные интеграции | Серверная верификация, идемпотентность, транзакционное начисление и подписки |
| Операционная автоматизация | Рассылки, напоминания, управление контентом и журнал действий оператора |
| Эксплуатация | Контейнеризация, миграции, health endpoint, CI и тесты с реальными PostgreSQL/Redis |

На собеседовании эти решения можно разобрать по исходному коду и воспроизвести ключевые сценарии через изолированный тестовый контур.

## Как оценивать эффект

В коде есть события генераций, финансовые отчёты и платёжная воронка. На их основе можно измерять долю пользователей с первым результатом, повторное использование, конверсию в оплату и оплаты после напоминания. Сам факт оплаты после напоминания не доказывает его причинный эффект — для этого нужен контролируемый эксперимент.

Публичных подтверждённых данных об экономии рабочего времени, выручке, нагрузке и росте конверсии здесь нет. Числа в демонстрации синтетические. При представлении проекта работодателю следует отдельно назвать собственную зону ответственности и привести только разрешённые к публикации, измеренные результаты.

## Ограничения и дальнейшее развитие

- Один процесс объединяет бота, веб-сервер и планировщик. При росте нагрузки понадобятся очередь заданий, отдельные воркеры и защита от дублирования задач между экземплярами.
- Telegram-обработчик изображений и веб-админка крупные. Следующий этап сопровождения — постепенное выделение независимых сценариев в модули.
- Начисление и подписка транзакционны, но уведомления и реферальный кэшбэк после commit выполняются best-effort. Для гарантированной доставки потребуется transactional outbox; кэшбэк пока хранится отдельно в Redis.
- Качество сохранения лица зависит от входного фото и модели. Оно не является гарантией точного совпадения; автоматической оценки качества по эталонному набору пока нет.
- `/health` проверяет ответ HTTP-процесса, а не готовность всех зависимостей. Подробные проверки доступны оператору в панели; отдельный readiness endpoint остаётся задачей развития.
- В репозитории нет универсальной CRM/ERP-интеграции или RAG. Перенос на другой бизнес-процесс потребует новых правил и адаптеров.
